# Adversarial review: Soleil Grid Hub design package

Method: I read db/schema.sql in full and enumerated all 126 operations in api/openapi.yaml (x-roles, security, descriptions, request schemas). I read the 07 threat register and RBAC matrix, the ask-the-data and drafting sections of 06, the webhook and SSE sections of 05, the money-flow sections of 02 and 03, and the DB-role sections of 04 and 09. Nothing was executed.

Headline: the strongest parts are the webhook and idempotency path, the ledger immutability on `app_rw`, and the base-table isolation of the analytics roles. The weakest parts are:

- Money can be minted by a single insider through the reconciliation and tariff routes.
- The audit hash chain, refresh-cookie design, step-up, four-eyes on roles/keys/KB, RLS coverage and ask-the-data guard rails that 05, 06 and 07 describe do not exist in the executed schema or the OpenAPI contract.
- The analytics guard rails (timeout, read-only default) never reach the login roles.

Abbreviations: S = db/schema.sql, O = api/openapi.yaml, 03/04/05/06/07 = the docs.

## (b) Schema security findings (db/schema.sql)

**S-1 (High). Role-level guard rails are applied to the wrong role.**
- Location: S 988-995.
- `ALTER ROLE analytics_ro SET default_transaction_read_only / statement_timeout / idle_in_transaction_session_timeout / temp_file_limit` and `CONNECTION LIMIT 20` live in `pg_db_role_setting` for that role only.
- Membership does not inherit them. The three real login roles (`analytics_support/finance/ops`) get only `search_path`, so they run with no timeout, no read-only default and no connection cap. The 09 line 111 URL logs in as `analytics_ro` itself, which has only `analytics_common`.
- Exploit: if the SQL guard is bypassed or has a gap, a `generate_series` cross join or `pg_sleep` on the replica runs unbounded, and the 20-connection cap does not apply.
- Fix: repeat every `ALTER ROLE … SET` and `CONNECTION LIMIT` for the three login roles. Add a CI assertion that `pg_db_role_setting` has these rows for each login role. A role can still `SET statement_timeout=0` itself, so also enforce a server-side watchdog (PgBouncer `query_timeout` on `hub_analytics`) and `REVOKE TEMP ON DATABASE … FROM PUBLIC`.

**S-2 (High). One powerful application role.**
- Location: S 915-918, 04 §4.1.
- `app_rw` serves api, ingest and worker with SELECT/INSERT/UPDATE on all tables. That includes `users` (password_hash, mfa_secret_enc), `user_roles`, `role_permissions`, `api_keys`, `wallet_balances`, `ledger_*` (INSERT), `provider_events`, `kb_article_versions`, `meter_tokens`, and `data_erasure_requests`.
- Exploit: an injection or RCE in the internet-facing `hub-ingest` pool (webhook and telemetry) can insert `user_roles(administrator)`, mint an `api_key`, or insert a balanced ledger transaction crediting any wallet.
- Fix: create `hub_api`, `hub_ingest`, `hub_worker` and `audit_writer`, each with table-level grants (ingest: `provider_events`, `meter_readings`, `meter_state`, `outbox`; no `users`/`user_roles`/`api_keys`/`ledger`). Route ledger writes through one `SECURITY DEFINER hub.post_ledger_transaction(...)` owned by a non-login `ledger_owner` that checks kind, `posting_key` and approval.

**S-3 (High). `wallet_balances` and `ledger_accounts` directly writable.**
- Location: S 915 vs 367-387.
- Exploit: any app-layer bug can `UPDATE wallet_balances SET balance_minor = …`. The token-issuance decision reads that row (02 line 527), and drift is noticed only by the nightly job (`v_wallet_balance_drift`).
- Fix: make `apply_wallet_balance` `SECURITY DEFINER SET search_path = pg_catalog, hub, pg_temp`, owned by `ledger_owner`. `REVOKE INSERT, UPDATE ON hub.wallet_balances, hub.ledger_accounts FROM app_rw` and grant INSERT on `ledger_accounts` through a function.

**S-4 (High). `erase_customer` is an unguarded superuser-owned SECURITY DEFINER.**
- Location: S 869-888, EXECUTE granted to `app_rw` at S 918.
- The script says it runs as superuser, so the function runs as superuser. It bypasses RLS and validates nothing: not `p_request_id`'s status (`verified`), not `kind='erasure'`, not that the request belongs to `p_customer_id`, not `legal_hold`, not two distinct approvers.
- `search_path = hub, pg_catalog` omits `pg_temp` last. `app_rw` can create temp tables (PUBLIC has TEMP on the DB), so an unqualified table name could resolve to a temp table.
- Gaps in the erase itself: it leaves `outbox.payload`, `idempotency_keys.response_body`, `audit_log.ip`, orphan `provider_events` (only events linked by `top_ups.provider_event_id` are scrubbed), `ai_runs` payload refs in object storage, and any attachments, notifications or exports (none have tables).
- Exploit: any `app_rw` code path, such as a SQL injection that can call functions, can irreversibly erase any customer with any request id.
- Fix: inside the function, `SELECT … FOR UPDATE` the request and require `status='verified'`, `kind='erasure'`, `customer_id = p_customer_id`, `legal_hold_reason IS NULL`, and `approved_by <> requested_by`. Set `search_path = pg_catalog, hub, pg_temp`. Use a dedicated non-superuser, `NOBYPASSRLS` owner role with only the needed UPDATE grants. Add per-customer encryption keys so erasure can be a key deletion (matches 07 §5.4).

**S-5 (High). RLS is thin and bypassable.**
- Location: S 904-909.
- Only `customers` and `tickets`, no `FORCE ROW LEVEL SECURITY`, so the owner or migrator role bypasses it. `ticket_messages` (message bodies) is unprotected even though `tickets` is protected. Policies are `FOR ALL TO app_rw`, so a malicious session can set its own scope.
- The policy filters by site, not by customer, so portal IDOR is not covered at DB level. 07 lists wallets and attachments as RLS-covered, which they are not.
- Fix: add `user_sites(user_id, site_id)` and a `ticket_messages` policy via the parent ticket. Add customer-id policies keyed on `app.customer_id` for `top_ups`, `meter_tokens`, `ledger_accounts` and `wallet_balances` (portal path). `FORCE` RLS. Make `set_config` of `app.*` effective only via a `SECURITY DEFINER` setter, or accept and re-document that RLS is only a bug net (04 §4.3 does so, but 06 and 07 do not).

**S-6 (Medium). Analytics views leak scope and allow re-identification.**
- Location: S 941-976, 04 §4.2.
- No site filter, so any support or finance user sees every site (04 §10 item 4 acknowledges this, but O and 07 do not).
- `v_customers` exposes site, plan, `created_at` and last four phone digits, and joins to `v_tickets.customer_id` and `contains_pii`. Row-level `v_top_ups` has customer id, amount and timestamps. 07's "minimum group size 5" does not exist.
- Fix: add per-view `HAVING count(*) >= 5` aggregate views or drop row-level views for finance and support. Add a site predicate through a `security_barrier` view keyed on `current_setting('app.site_scope')` set by a `SECURITY DEFINER` function that the analytics role cannot override (set from the connection-level role setting, not a GUC the model-written SQL can touch).

**S-7 (Medium). PUBLIC defaults and missing default privileges.**
- Location: S 8 and the absence of `REVOKE … ON DATABASE`/`ALTER DEFAULT PRIVILEGES`.
- Only `public` schema is revoked. PUBLIC keeps CONNECT and TEMP on the database and EXECUTE on `pg_catalog` functions (`pg_sleep`, `set_config`, `pg_advisory_lock`). Analytics roles can read catalog metadata including view definitions (04 §4.4 acknowledges metadata only).
- There is no `ALTER DEFAULT PRIVILEGES`, so new tables and views are silently ungranted.
- `hub.ensure_meter_reading_partitions` is granted to `app_rw` (S 918) but is neither owned by it nor `SECURITY DEFINER`, and `app_rw` has no CREATE on `hub`. Run as `app_rw` it will fail when it first tries to create a partition, so partitions stop being created and rows pile up in the unbounded default partition. It was presumably tested as owner.
- Fix: `REVOKE CONNECT, TEMP ON DATABASE … FROM PUBLIC` and grant per role. Make the partition function `SECURITY DEFINER` with a pinned search_path, owned by the migration role.

**S-8 (Medium). `audit_log` weaker than claimed.**
- Location: S 770-794, 915.
- `app_rw` has SELECT and INSERT, so any code path can read the log and insert a row with any `actor_id`, `actor_type`, `occurred_at` (backdated) and `id`. There is no chain, no stream and no per-row signing. `ip inet` and free `details jsonb` can hold personal data, and erasure does not touch them.
- Fix: `audit_writer` role plus a `SECURITY DEFINER hub.audit_append(...)` that computes `seq`, `prev_hash` and `hash` under `pg_advisory_xact_lock(stream)` and fixes `occurred_at := now()`. Revoke SELECT from the app role, create a separate reader, and implement the verifier and the signed anchor in 09.

**S-9 (Medium). Immutability bypass routes.**
- Location: S 319-326, 791-794.
- The triggers are plain enabled triggers: they do not fire under `session_replication_role = replica` (superuser) or `pg_restore --disable-triggers`, and the table owner can `DISABLE TRIGGER` or `DROP TRIGGER`. `app_rw` itself cannot do these.
- The ledger trigger blocks UPDATE/DELETE but not a later INSERT of a balanced pair of entries into an already-committed transaction id, which rewrites a posted transaction's effect. CHECK `uq_ledger_transactions_posting_key` does not prevent it.
- Fix: `ALTER TABLE … ENABLE ALWAYS TRIGGER` for the immutability triggers. Add a BEFORE INSERT trigger on `ledger_entries` that requires the header row to have been created in the same transaction. Add an event trigger or pgaudit alert on `ALTER TABLE … DISABLE TRIGGER`. Keep the migrator off the runtime path.

**S-10 (Medium). Missing columns and tables that the controls assume.**
- Absent from S: `refresh_tokens`, `customer_otp`, `mfa_secrets` and WebAuthn credentials, `token_version`, `staff_customer_link`, any approval or pending-approval table, attachments, notifications, `ticket_reply_drafts`, exports, user sites, gateways, KB approver, token counter and expiry.
- Constraint holes:
  - `meter_tokens` can exist without a ledger transaction.
  - No unique provider txn id on `provider_events`.
  - `top_ups` has no quoted tariff or energy snapshot, and nothing ties `top_ups.meter_id` to `top_ups.customer_id`.
  - No CHECK `signature_valid` on stored events.
- Fix: add these in the next schema revision. At minimum `CHECK (ledger_transaction_id IS NOT NULL)` on `meter_tokens`, `UNIQUE (provider, provider_txn_id)`, `top_ups.tariff_minor_per_kwh_snapshot` and `energy_wh`, and a composite FK `(meter_id, customer_id)` to `meters`.

**S-11 (Low). UUIDv7 and ids.**
- `hub.uuid_v7()` is correct (version nibble set, random bits from `gen_random_uuid`, so unguessable). IDs leak creation time to the millisecond and the creation rate (customers, top-ups, tickets, tokens). `ledger_accounts.code` embeds the customer uuid, and the top-up id is sent to the provider as `external_reference`.
- Effect: low. Do not rely on ids for secrecy (07 already says so), and confirm application-side v7 uses a CSPRNG.

**S-12 (Low). `meter_readings` accepts attacker-chosen keys.**
- Location: S 485-501.
- No FK to meters, no lower bound on `read_at` (past values land in the default partition), and the PK `(meter_id, read_at)` with first-write-wins lets a rogue gateway pre-write a future reading (up to `now()+1 day`) that blocks the genuine one. Any `meter_id` uuid is accepted, so storage can be filled.
- Fix: validate `meter_id` against `meters` and the gateway's binding in the ingest code, add a CHECK `read_at > now() - interval '45 days'`, and make ingest compare `cum_energy_wh` monotonicity.

**Verified (no finding).** Analytics roles have no privilege on `hub` base tables, so no personal data table is reachable except through the masked views. No sequences exist, and ids are application-generated. `app_ro_replica` has column-level grants that hide `password_hash`, `key_hash`, `payload` and `token_enc`. `app_rw` has no TRUNCATE, no DELETE on ledger or audit, and no UPDATE on ledger or audit.
